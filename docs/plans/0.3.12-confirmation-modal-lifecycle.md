# 0.3.12 — Confirmation Modal Lifecycle and Tool-Stage Responsiveness

> **Status:** Active — S1–S5 implemented 2026-09-27, not yet released.
> Version is still `0.3.11` in code; the bump happens at release prep.
> This plan absorbs the two follow-ups left open by
> [0.3.10](0.3.10-terminal-and-release-hardening.md) §Post-release
> follow-ups (items 2 and 3). Follow-up 3 ("tool-stage stall diagnosis
> needs the owner's inputs") is **no longer blocked on owner input**:
> the stall mechanism was located in code and reproduced without a
> human in the loop (see D1). Follow-up 2 (owner terminal acceptance on
> the published binary) still needs the owner, but is now backed by a
> scripted probe (S5) so the report is reproducible rather than
> anecdotal.
> Version bump to `0.3.12` happens at release prep, not in this plan.

## Scope

1. **The tool watchdog must release the confirmation modal it was
   blocked on** (P0, proven defect).
2. **A high-risk confirmation must not be approvable by an incidental
   keystroke** (P0, trust boundary).
3. **The tool stage must be visible and cancellable** (P1, the "stall"
   the owner reported).
4. **Structured diagnostics** so the next owner report needs no code
   change (P1).
5. **Scripted owner terminal acceptance** for the published binary
   (P2).

## Defects located while planning

### D1 — A timed-out confirmation leaks a permanently mounted modal (P0)

> Line numbers and the quoted snippet below are the **pre-fix** state
> (`0.3.11`). They are kept as the record of what was wrong; see
> *Implementation record* for the fix.

`core/operation_policy.py:593 prompt_for_confirmation` runs on the tool
worker thread and marshals the modal onto the terminal's event loop:

```python
future = asyncio.run_coroutine_threadsafe(run_confirmation_modal(decision), loop)
try:
    return bool(future.result(timeout=600))
except Exception:
    return False
```

`future.result(timeout=...)` **does not cancel the coroutine**. The
coroutine is parked inside `controller.run_selector` on
`await future` (`pawnlogic/live_terminal.py:2104-2109`); the
`finally: self.terminal.close_selector(future=future)` that unmounts the
selector therefore never runs. `prompt_for_confirmation` returns `False`
(deny) and the caller proceeds, while `_ConfirmSelector` stays
installed in the live `Application`.

Reproduced with a scratch script mirroring the exact ownership chain
(`asyncio.run_coroutine_threadsafe` + a coroutine parked on
`await future`): the tool thread printed
`TimeoutError -> returns False (DENY)` while `selector closed` stayed
unset; the unmount finally ran only at interpreter shutdown
(`Task was destroyed but it is pending!`). The scratch script is not
checked in — S1's regression test is its permanent form.

Consequences:

- `PersistentTerminal._selector_registry.has_state` stays `True`
  (`pawnlogic/selectors.py:202-205`), so the eager selector key
  bindings keep capturing input (`pawnlogic/live_terminal.py:1365-1402`).
  The composer is read-only while the modal is up; the user's typing
  goes to the selector instead.
- `SelectorRegistry.install_active` only supersedes a leaked selector
  when the user opens *another* selector, so bare commands and ordinary
  composition stay dead until then. `abandon_selectors()`
  (`live_terminal.py:556`) is wired to the **Application task**
  observer, not to the tool watchdog, so nothing reclaims it.

Both deadlines are the same number: the confirmation wait is a literal
`600` (`operation_policy.py:611`) and `DEFAULT_TOOL_WATCHDOG_SECONDS` is
`600.0` (`core/tool_executor.py:241`). Whichever fires first, the loser
leaves the abandoned thread or the mounted modal behind, and during the
whole window the user gets **no feedback at all** — the status line
still reads `⏱ Ns · Esc to interrupt`.

### D2 — Enter approves a high-risk operation while the user is typing (P0)

> As with D1, the line numbers are the pre-fix state.

`_ConfirmSelector` defaults to `selected_idx = 0` =
**"Approve and run"**, and `handle_key("enter")` approves
(`operation_policy.py:534-576`). The eager bindings route `enter`,
`c-j`, `c-m` to the selector whenever `has_state` is true. So an Enter
meant as "submit my next message" — typed while a tool waits on
confirmation — **silently approves a high-risk command**. Digits
`1`-`9`, arrows, `space`, `a`, and `n` are likewise consumed, and the
user has no guarantee the modal is actually visible: nothing checks
that the Float rendered before the selector starts accepting input.

### D3 — The tool stage is silent (P1)

A tool can legitimately run for minutes. Nothing in the persistent
status line distinguishes "tool is working" from "tool is blocked
waiting on a confirmation you cannot see", and Esc during that window
routes to the interrupt path, not to the pending modal.

## Plan

| S1 | `prompt_for_confirmation` cancels the marshalled coroutine and resolves the selector when its wait expires; add a bounded, separately-configurable confirmation wait instead of the literal `600` | D1 | Regression: a modal whose wait expires leaves `has_state == False` and the composer accepting input |

| S5 | Scripted owner-acceptance probe for the published binary (glyph width, selection, copy, scrollback, mouse) emitting a machine-readable result the owner can paste back | 0.3.10 follow-up 2 | Probe runs on Windows Terminal / WSL and reports pass/fail per check |

**Owner decision on S2 (recorded 2026-09-27): Deny-by-default plus an
explicit approve key.** The owner approved the recommended shape after
an independent review reproduced D1/D2/D3 in code. The modal therefore
opens pre-selected on *Deny*; `y` approves, `n`/`Esc`/`Ctrl+C` deny, a
bare `Enter` denies, and no key is accepted until the Float has rendered
at least one frame. The status line shows `⚠ awaiting confirmation — Esc
to review` while the modal is mounted.

**Owner decision on automated terminal coverage (recorded 2026-09-28):
CI and local verification must not require a real Provider API key.**
PawnLogic is run locally and no suitable key is available for this test
gate. S3 is therefore covered at the real persistent Prompt Toolkit
Application seam with an isolated Runtime Home and synthetic input; it
must exercise the mounted selector, status, Esc priority, teardown, and
composer recovery without making a Provider request. The published-binary
scrollback, selection/copy, and terminal-emulator checks remain explicit
owner acceptance items and must continue to be reported as manual until
the owner records their result. A skipped key-dependent E2E is not evidence
for or against this merge.

## Implementation record

S1's table row said "cancel the marshalled coroutine when the wait
expires". The implementation deliberately went one step further, because
cancellation from the tool thread is not reliable: `Task.cancel()` is
not thread-safe, and cancelling a `run_coroutine_threadsafe` future only
takes effect if the coroutine has not started yet. The **loop that
mounted the modal therefore owns the deadline** —
`asyncio.wait_for` inside `run_confirmation_modal` — so the coroutine is
already unwound and its `finally: close_selector(...)` has run by the
time the tool thread is told anything. The thread-side `future.result()`
is kept only as a strictly longer backstop
(`confirmation_wait_sec + 5s`), so it can never be the thing that ends
the wait. The same reasoning produced S4's clamp: `confirmation_wait_sec`
is capped below `tool_watchdog_sec`, guaranteeing the loop tears the
modal down while its waiter is still alive.

Two notes on the tests themselves, both of which caught real mistakes
during this work:

- `test_expired_confirmation_unmounts_the_modal` asserts
  `seen["mounted"] == [True]` before its outcome assertions.
  `run_confirmation_modal` reads the controller from a module-level
  registration slot, so a test that forgot to register one would
  otherwise pass **vacuously** — the modal was never mounted, so it can
  never leak. The guard makes that failure mode impossible.
- Removing the `asyncio.wait_for` wrapper was used to confirm the test
  is not vacuous in the other direction: the test then fails (the modal
  stays mounted). It is restored and passing.

`test_selector_escape_binding_outranks_the_turn_interrupt` is a source
inspection, not a behaviour test, because the property is structural:
Prompt Toolkit runs `eager=True` bindings before non-eager ones
regardless of registration order, the selector's Esc is eager
(`live_terminal.py:1370`) and the Turn-interrupt Esc is not
(`live_repl.py:290`). The test pins both halves so a future edit that
adds `eager=True` to the interrupt path, or drops it from the selector,
fails loudly.

The 2026-09-28 independent audit found three gaps in the first
implementation and its tests. The watchdog clamp used the constant default
rather than the active `tool_watchdog_sec`; the watchdog test mocked the
reclaim call instead of proving that the real modal unmounted; and the owner
probe treated the presence of an enable sequence as a leaked terminal mode
even when a later disable sequence restored it. The remediation reads both
deadlines from the same runtime configuration, exercises the real watchdog →
tool thread → event loop → selector teardown chain, and evaluates the last
enable/disable transition for every terminal mode. The probe now accepts
repeatable `--manual-pass` / `--manual-fail` results and preserves unanswered
checks as `manual` in its JSON report.

The provider-free live-Application regression also caught a separate test
blind spot: direct selector unit tests proved that `handle_key("y")` approved,
but the persistent Application had no eager `y` binding, so the documented
approval key did nothing in the real UI. The live terminal now routes `y` to
the active selector, and the PipeInput integration test covers both approval
and Esc denial through the real key processor.

## Out of scope

- No scheduler rewrite, wire-protocol change, or provider change.
- No minor (second digit) version bump; this is a patch release.
- The `run_code` payload-classifier residual (dynamic command
  construction, `from os import system` aliases, javascript/go/compiled
  payloads) stays a documented Known Risk, narrowed only if a concrete
  case appears.
- Owner terminal acceptance findings that turn out to be environment
  artifacts (the 0.3.10 TERM=dumb precedent) are recorded, not "fixed".

## Acceptance criteria

1. Every S-row has a named regression test that fails before its fix.
2. `tests/test_process_trust_routing.py` gains a
   `TestConfirmationModalLifecycle` class; the existing
   `prompt_for_confirmation` patch points in

   contract (a tool thread must never leave a selector mounted), and
   the 0.3.10 plan's two open follow-ups are marked resolved here.

   locations only, after this plan's implementation merges.
